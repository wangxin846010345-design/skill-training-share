快速上手

10 分钟做出你的第一个 Skill

如果你已经有现成 API，按照以下 3 步即可完成。详细说明见下方 SOP。

1
找到 API 并用 curl 调通

找后端拿到 API 地址和认证方式，手动 curl 验证能返回数据

2
写 SKILL.md

用 下方模板 填入你的 API 信息，或直接把 API 信息发给 AI 让它帮你生成

3
安装测试

上传到 WorkBuddy → 用自然语言测试 → 补充踩坑记录 → 让同事也试试

⏱️

耗时参考：第一个 Skill 约 1 小时（含踩坑调试），后续同类 Skill 20-30 分钟。

SOP · Step 1
1

确定数据源与埋点策略

⏱ 前置工作，非 Skill 开发本身

不同复杂度的业务系统，埋点颗粒度不同。颗粒度越细，Skill 能分析的维度越多，但开发成本也越高。

简单系统

页面级埋点

如：简单审批/报名系统

记录字段
· 页面访问（PV/UV）
· 表单提交次数
· 完成率/转化率
中等系统 ★ 本案例

操作级埋点

如：表单平台/项目管理系统

记录字段
· 操作人（userId / 姓名）
· 操作类型（创建/编辑/删除/发布）
· 操作对象（表单/模板/项目）
· 操作时间（精确到秒）
复杂系统

字段级埋点

如：ERP/全链路平台

记录字段
· 字段变更（修改前/后值）
· 关联实体链路
· 状态流转路径
· 操作耗时
💡

实操建议：先从操作级埋点起步，能满足 80% 分析需求。字段级埋点只在确实需要"谁改了哪个字段"时才做——颗粒度越细，存储和查询成本指数级增长。

SOP · Step 2
2

开发查询 API

⏱ 需后端配合，或复用已有 API

拿到埋点数据后，需要提供一个 API 让 Skill 调用。两种方案：

✅ 方案 A：聚合查询 API（推荐首选）
  • 原理：服务端 SQL 聚合，返回统计结果
{"totalOps":429, "activeUsers":45, "byUser":[{"name":"龚静","count":70}]}
  • 数据量小，响应快
  • 对 AI 友好，直接出结果
  • 服务端控制边界，安全
  • 查询维度需提前设计
  • 新增维度需改接口
VS
⚠️ 方案 B：明细 JSON（本案例）
  • 原理：返回操作明细列表，AI 端做聚合
[{"userId":"u001","records":[ {"action":"创建表单","time":"..."}]}]
  • 数据完整，分析维度灵活
  • 新增维度无需改接口
  • AI 可自由下钻
  • 数据量大时性能差
  • 依赖 AI 聚合，有 token 成本
  • 数据量超限需分页/兜底

📊 方案选择决策表

你的场景推荐方案原因
用户 < 100，单次记录 < 500 条方案 B灵活性收益远大于性能风险
用户 100~1000，记录较多方案 A + B 组合主接口 A 出概览，下钻接口 B 出明细
用户 > 1000 或全量 > 10MB方案 A明细数据量太大，必须服务端聚合
分析维度非常固定方案 A无需灵活性，聚合接口更高效
分析维度多变方案 B + 兜底策略灵活性优先，但必须加 Step 5 兜底
⚠️

本案例选了方案 B——用户量小（<100），记录量可控，但分析维度多变。如果你的系统数据量大，务必从方案 A 起步。

SOP · Step 3
3

将 API 封装为 Skill

⏱ 10-15 分钟

按照以下模板编写 SKILL.md，3 个核心块缺一不可：

🔑

触发词设计

description 覆盖用户说法
"查询XX操作记录"
"分析XX使用情况"

⚙️

API 调用规范

URL / Method / 认证
完整 curl 示例
参数放 Body 还是 URL

📐

输出格式

核心数字 + Top 排行
+ 趋势 + 异常标注

📁

目录结构：大多数 Skill 只需一个 SKILL.md。
your-skill/├SKILL.md └scripts/(可选) └references/(可选)

模板

SKILL.md 模板 & 案例

📝 通用模板

--- name: your-system-analytics description: 查询[系统名]的[数据类型]，如"查XX的操作记录""分析XX的使用情况""对比XX的数据" --- # [系统名]数据分析 ## 触发条件 用户提到查询/分析/对比 [系统名] 的 [数据类型] ## 参数提取 - 日期范围：startDt / endDt（YYYY-MM-DD） - 筛选条件：用户名 / 项目名 / 操作类型 等 ## API 信息 - URL: https://your-api.com/endpoint - Method: POST - 认证: [参照认证速查表选择] - 参数位置: Body（必须！） ## 请求示例 curl -X POST 'https://your-api.com/endpoint' \ -H 'Content-Type: application/json' \ -H '[认证 Header]' \ -d '{"startDt":"2026-05-01","endDt":"2026-05-08"}' ## 输出格式 1. 核心数字：总操作数 / 活跃用户数 / 时间范围 2. Top5 排行（按用户 / 按项目） 3. 趋势描述 + 异常标注 4. 追问可下钻到具体明细 ## 注意事项（踩坑记录） 1. [你的踩坑 1] 2. [你的踩坑 2] 3. 数据量超过 [X] 条时，建议加时间范围缩小查询

📝 实际案例：用户操作记录 Skill

--- name: user-operation-records description: 查询用户在指定日期范围内的操作记录（表单和模板操作） --- # 查询用户操作记录 ## 触发条件 用户说"查询XXX的操作记录"、"查一下XXX的操作记录"等 ## 参数提取 - 日期范围：startDt 和 endDt，格式 YYYY-MM-DD - 用户名：如"徐琦"等中文姓名 ## API 信息 - URL: https://www.duiopen.com/ai-protocol-hub/internal/userOperationRecords - Method: POST - 认证: Cookie: userId=1000002201 ## 请求示例 curl -X POST 'https://www.duiopen.com/ai-protocol-hub/internal/userOperationRecords' \ -H 'Content-Type: application/json' \ -H 'Cookie: userId=1000002201' \ -d '{"startDt":"2026-04-20","endDt":"2026-04-26"}' ## 注意事项 1. 认证必选：无认证返回 401 2. 日期参数必须放 body：放 URL 会 OOM 3. 不带 body 会 400 4. 只支持 Cookie 认证，不支持 API Key

🤖 让 AI 帮你生成 SKILL.md

请帮我创建一个数据分析类 Skill 的 SKILL.md： 1. 系统名称：[你的业务系统名，如"审批系统"] 2. API 地址：[你的 API URL] 3. 请求方式：[GET/POST] 4. 认证方式：[Cookie / Bearer Token / API Key]，认证参数：[具体值] 5. 请求参数：[参数名、类型、是否必填] 6. 返回数据示例：[贴一段 API 返回的 JSON] 7. 用户可能的说法：[同事平时怎么问的]
⚠️

AI 生成后必做：1) 确认触发词覆盖了同事的说法 2) 用 curl 实际调一次验证 3) 把踩到的坑补进注意事项。不要在 Prompt 中传真实 Token。

SOP · Step 4
4

并发控制与权限管理

⏱ 视情况，可后补

⚡ 并发控制

请求限频10 次/分钟，防 AI 高频调用
结果缓存相同查询 5min 内返回缓存
超时熔断API > 10s 自动降级
## 并发策略 同一用户 5 分钟内重复查询，直接使用缓存结果。

🔒 权限管理

数据隔离按 userId 过滤
角色分级管理员看全量，普通用户看本部门
脱敏规则手机号/身份证 API 层脱敏
## 权限说明 该 API 通过 Cookie userId 做数据隔离， 每个用户只能查看自己所属项目的数据。
⚠️

Cookie/Session 认证的注意：Skill 中 userId 固定意味着所有使用者共享同一账号的数据权限。如需按人隔离，必须改为 Bearer Token 或 OAuth，在 SKILL.md 中引导用户替换自己的 Token。

SOP · Step 5
5

大数据量兜底策略

⏱ 5 分钟写入 SKILL.md

5 道防线，按优先级排序：

🛡️ 防线 1：强制时间范围

用户未指定时默认查最近 7 天，单次跨度不超过 90 天。

## 默认行为 用户未指定日期时，默认查询最近 7 天。 单次查询跨度不超过 90 天。

🛡️ 防线 2：分页 / 游标

单次返回最多 200 条，AI 多轮调用拼全。

{"startDt":"2026-05-01","endDt":"2026-05-08","pageSize":200,"pageNo":1}

🛡️ 防线 3：自动降级

数据量 > 500 条时，只返回 Top10 排行和趋势摘要。

## 降级策略 返回数据超过 500 条时，只展示 Top10 和趋势摘要， 提示"数据量较大，已自动汇总，如需明细请缩小时间范围"。

🛡️ 防线 4：超时兜底

API 超时 30s 后返回友好提示。

🛡️ 防线 5：异步查询

极端场景用异步模式：提交任务 → 返回任务 ID → 轮询结果。日常查询用前 4 道防线足够。

📊 兜底策略速查

数据规模推荐防线SKILL.md 要写什么
< 500 条/次防线 1默认查 7 天 + 提示可扩大
500 ~ 5000防线 1 + 2加分页参数 + 默认页大小
5000 ~ 5 万防线 1 + 2 + 3加分页 + 降级阈值 + 提示语
> 5 万全部 5 道考虑改用方案 A + 异步导出

常见踩坑

实战踩坑 & 解决方案

全部来自真实开发经历，提前了解可大幅缩短调试时间

🔴 401 Unauthorized

场景：调用 API 返回 401"游客身份没有权限"
原因：只支持 Cookie 认证，不支持 Bearer Token / API Key
解决：请求头加 Cookie: userId=xxx

🔴 服务端 OOM

场景：日期参数放 URL query 导致内存溢出
原因：query 参数走了不同代码路径，加载全量数据
解决：日期参数必须放 JSON Body

# ❌ 参数放 URL → OOM curl '...?startDt=2026-04-01&endDt=2026-04-30' # ✅ 参数放 Body → 正常 curl ... -d '{"startDt":"2026-04-01","endDt":"2026-04-30"}'

🟡 400 Bad Request

原因：不带 Body 或 Body 格式错误
解决：必须传 {"startDt":"...","endDt":"..."}

🟡 Skill 没被触发

原因：用户表述不在触发词覆盖范围
解决：持续补充 description 中的关键词

🔁 踩坑后迭代修复

· 401/403 → 检查认证方式，补充到注意事项
· 没触发 Skill → 补充触发词覆盖
· 数据格式不对 → 明确输出格式要求
· 大数据量超时 → 加入兜底策略
· 建议节奏：上线第一周每天 5 分钟回顾反馈，之后每周 10 分钟

FAQ

❓ 常见问题

Skill 和普通 Prompt 有什么本质区别？ +
Prompt 告诉 AI "怎么回答"，Skill 告诉 AI "怎么做事"。Prompt 优化输出质量，Skill 给 AI 接入真实数据源和操作能力。善于回答问题 ≠ 能帮你查数据。
我没有后端开发经验，能做 Skill 吗？ +
能！如果系统已有 API，只需写一个 SKILL.md（Markdown 文档）描述如何调用。不涉及代码编写。如果还没有 API，需找后端同事协助开发，但 SKILL.md 本身不需要编程能力。也可以把 API 信息发给 AI，让它帮你生成 SKILL.md 初稿。
Skill 中的认证信息会不会泄露？ +
认证信息只存在于本地 SKILL.md 中，不会在对话中展示给其他用户。建议：1) 不要硬编码真实 Token，用环境变量替代；2) Cookie 类认证标注"仅供内部使用"；3) 需要按人隔离数据时，使用 Bearer Token 或 OAuth 替代 Cookie。
做好的 Skill 能分享给团队吗？ +
三种方式：1) SkillHub 发布，团队搜索安装；2) 直接分享 Skill 文件夹，同事上传到 WorkBuddy；3) 放入项目级目录 .workbuddy/skills/，项目成员自动可用。
API 返回数据量很大怎么办？ +
SOP Step 5 提供了 5 道防线：强制时间范围 → 分页 → 自动降级 → 超时兜底 → 异步查询。根据数据规模选择组合即可。<500条用防线1，500-5000加防线2，5000-5万加防线3，5万以上全部5道。
用户说什么才能触发 Skill？ +
取决于 SKILL.md 中 description 字段的关键词。建议至少覆盖 3 种说法，如"查询XX操作记录""分析XX的使用情况""看看上周XX的数据"。用户说法越多样，description 中需要覆盖的关键词越多。上线后根据实际使用情况持续补充。
Skill 上线后需要维护吗？ +
需要轻量维护。主要场景：1) API 字段变更时同步更新 SKILL.md；2) 同事说的新说法没触发时补充触发词；3) 发现新踩坑点时补进注意事项。建议节奏：上线第一周每天 5 分钟回顾反馈，之后每周 10 分钟。
Cookie 认证和 Bearer Token 认证怎么选？ +
取决于你的 API 支持哪种。内部系统通常是 Cookie（SSO 登录态），外部 API 通常是 Bearer Token。Cookie 的限制是 userId 固定，所有人共享权限；Bearer Token 支持按人隔离但需要每人配置自己的 Token。详见认证速查表。
如何让 Skill 支持按用户隔离数据？ +
Cookie/Session 认证下 userId 是固定的，无法按用户隔离。解决方案：1) 改用 Bearer Token 或 OAuth，在 SKILL.md 中引导用户替换自己的 Token；2) API 支持按 userId 过滤参数时，在请求中传入当前用户 ID；3) 服务端根据请求来源自动做数据隔离。
